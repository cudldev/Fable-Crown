# Visual acceptance

Use images from the exported models, not source-code descriptions. Inspect the model in the browser art workbench with effects restrained and in the actual game camera. Include front/side/back or rotated views as needed, plus walking for a character and roofs off for a building. Reuse a consistent camera/framing for before/after comparisons.

Assess these separately:

| Criterion | What to look for |
|---|---|
| Silhouette and proportions | Reads at gameplay scale; major forms match the intended character or building type |
| Form and construction | Deliberate planes, useful negative space, believable joints/openings/structure |
| Material and pixel craft | Coherent broad values, consistent texel scale, no stretched/noisy atlas patches |
| Cohesion with target | Muted palette, authored chunky forms, JRPG character charm, original identity |
| Integration | Grounded feet, correct pivots, readable interactions, shadows/light under control |

For each, state **placeholder**, **usable draft**, or **reference-quality candidate**, with one visible reason. Do not invent exact scores or call all criteria good without looking. The lead can accept a useful draft for the test while naming remaining gaps; only the user determines whether the desired art direction has been reached.

If a visible issue persists, make a focused correction and compare again. Do not respond to criticism by producing many more unreviewed assets. A polished single asset is more useful for establishing the workflow than a large mediocre set. Keep technical validation separate: valid GLBs, UVs, bounds and budgets can all pass while the model still fails visual review.
